# Source and Demo Truth Contract

Use one fact model across the whole portal. A demo may be synthetic or it may use verified real event data, but it must not quietly blend the two.

## Source Modes

### Verified real

Every event requires:

- a current source URL
- a UTC source-check timestamp
- a verified title, description, lifecycle, date, time, IANA time zone, and duration or end time
- verified registration, live, fallback, and replay destinations when the lifecycle needs them
- source-backed speakers, organizations, outcomes, images, and resources

If a provider page omits a fact, keep it unresolved and request it from the event owner.

### Illustrative demo

Use synthetic organization, event, speaker, and resource data. Record a concise disclosure in the manifest and seller handoff. Do not use a real customer logo or imply that a fictional event is scheduled, open for registration, live, recorded, or endorsed.

The attendee-facing demo may omit internal staging language when the seller is presenting it as a clearly framed prototype. The handoff must still preserve the illustrative status.

## Prohibited Inferences

Do not infer:

- duration from a recurring program or a prior event
- speakers from company roles or social profiles alone
- a replay from an expired live link
- a live player from a provider registration URL
- a public join route from a personal or registrant-specific link
- customer participation, approval, outcomes, attendance, or intent
- event images, brand colors, or logos from generic search results without source confirmation

## Source Ledger

For every visible factual element record:

- fact or asset
- value used
- source URL or approved file
- checked timestamp
- status: verified, illustrative, unresolved, or omitted
- notes about lifecycle or provider limitations

Refresh time-sensitive event facts during the active build. Treat an old manifest as a starting point, not proof.
